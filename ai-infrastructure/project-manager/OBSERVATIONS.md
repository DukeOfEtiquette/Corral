# Observations

Append-only log of recurring patterns, friction points, and notable one-offs seen while working in this repo. Convention inherited from rogue (ADR-009).

## Conventions

- Stable IDs: `COR-NN`, monotonically increasing, never reused.
- Lifecycle: **seen-once** (handled ad hoc, not yet logged) -> **logged** (an entry below, with context) -> **promoted** (canonicalized into a rule, template, role doc, or ADR; the entry records where it went).
- Entries are never edited after the fact except to update their lifecycle state and promotion pointer.

## Entry format

```markdown
### COR-NN: short title
- date: YYYY-MM-DD
- state: logged | promoted -> <where>
- context: what happened, where
- pattern: why this might recur / what to do about it
```

### COR-03: hand-maintained roadmap milestone statuses are the dashboard's last drift surface, now load-bearing

- date: 2026-06-11
- state: promoted -> `./decisions/ADR-036-work-item-taxonomy.md` (2026-06-12; the taxonomy makes epic/phase status a task-rollup derivation and retires hand-set milestone status. COR-T-040 already derives a milestone's effective status from its task refs; the roadmap restructure follow-on completes the removal of the hand-set field.) | ADR-039 derived the STATUS activity surface (last_updated + recent_updates frontmatter keys, git-derived; retired by COR-T-047, 2026-06-13) and named itself terminal, but the narrative body was one hop short. | terminal: ADR-040 (2026-06-13) derives the full STATUS narrative body (`## Current phase` / `## Next step` / `## Blocked on`), leaving zero hand-authored content in STATUS.md; implementation cascade COR-T-050. This is the actual terminus of the lineage for STATUS.md.
- context: The dashboard originally derived each phase's CURRENT/UPCOMING badge from a single hand-maintained `phase` field in coordinator STATUS frontmatter; that field drifted (stayed `phase: 1` after Phase 2 began via COR-T-023 and DB-T-001), so the live dashboard showed Phase 1 CURRENT while Phase 2 was already underway. The same class of drift had been seen once before (P1-6 milestone status left `in-progress` after COR-T-017 delivered it, corrected during the COR-T-020 wrap-up; recorded in STATUS recent_updates). COR-T-029 fixed the phase pointer by deriving `current_phase`, `current_phase_title`, and `next_step` from the per-milestone `status` values. But that pushed the hand-maintained surface down one level: every derived field now depends on the roadmap milestone `status` (`done`/`in-progress`/`planned`) values, which are still set by hand in the coordinator STATUS frontmatter and are read verbatim by `etl.py` (`ms.get("status")`). A milestone whose work is done but whose status was never flipped will now silently mis-drive the entire phase display, not just one badge.
- pattern: Each time a hand-maintained pointer is replaced by derivation, the drift relocates to whatever the derivation now reads, rather than disappearing. The remaining hand-set inputs are the milestone statuses. Many milestones carry a `task:` ref (e.g. P1-4 -> COR-T-014, P2-1 -> DB-T-001), so a milestone's `done`-ness could be cross-checked against (or derived from) whether that task file sits in a `tasks/done/` tree, catching the drift mechanically. Candidate promotion: a consistency check in `etl.py` (or a dashboard warning) that flags any `task`-bearing milestone whose authored status disagrees with its task's tree location; full auto-derivation is bounded because task-less milestones have no structural signal. Until promoted, milestone statuses remain a manual-accuracy dependency worth re-checking when advancing the roadmap. Separately, the dead department PHASE column (a hand-maintained field with no source at all) is tracked as the deliverable COR-T-030, distinct from this milestone-status surface.

### COR-04: workers emit plausible-but-wrong run/verification commands for unrun steps

- date: 2026-06-11
- state: promoted -> `./decisions/ADR-035-cited-reference-integrity-dispatched-work.md` (2026-06-12; prevention via the kickoff citation-completeness convention plus the explicit Dispatched-worker-flow step-6 sub-step; implementation cascade COR-T-039)
- context: On COR-T-034 (dashboard ADR-modal), the dispatched `worker-agent` could not run the ETL or Vite build (ADR-003 compose-only run policy; the worker correctly declined to fabricate a verification result). But in its closing report's "Build / verification status" it handed the Orchestrator two specific commands to run instead, `docker compose ... run --rm etl` and `... run --rm build`, naming `etl` and `build` compose services. The dashboard `ai-infrastructure/project-manager/dashboard/docker-compose.yml` defines only a single `dashboard` service (build + entrypoint ETL + http.server); no `etl` or `build` service exists, so both suggested commands would fail. The Orchestrator caught it on the verify-against-disk re-derivation (Dispatched-worker flow step 6) and substituted the correct single command, `docker compose -f .../docker-compose.yml up --build`.
- pattern: A worker that correctly refuses to fabricate a verification *result* may still fabricate the verification *procedure*, inventing command/service/flag names that read as authoritative but were never checked against the actual compose/Makefile/script. The unverified-claim risk shifts from "did the check pass" to "is this even the right command", and a report's run instructions are exactly the kind of load-bearing claim the Orchestrator must re-derive rather than trust (Agent Discipline; Dispatched-worker flow step 6 already says do not trust the report's verification claims, of which run procedures are one). This is the first logged instance; a second would warrant promotion. Candidate promotions: (a) a kickoff convention that the Orchestrator pins the exact run/verify command(s) in the kickoff when the worker cannot run them, so the worker echoes a checked command rather than inventing one; or (b) a worker-close-checker rule that any report-supplied run command naming a compose service / script target be grounded in a file the worker actually read. Until promoted, the Orchestrator verifies report-supplied run commands against the compose/script files on disk before relaying them to the user.

### COR-07: visual deliverables have a verification blind spot that only a render catches

- date: 2026-06-12
- state: logged
- context: On COR-T-040 (dashboard roadmap ref badges) the dispatched executor verified the data layer (curl on `data.json`, compose build succeeds) and returned COMPLETED, but the page rendered completely BLANK: a React reserved-prop bug (`ref` passed as a data prop is not forwarded to a function component, so the badge data was `undefined` and the render threw, unmounting the whole tree). No data-layer or build check could surface it. Separately on the same task, styling defects (the Agent Fleet tables not aligning across the two groups; milestone rows lacking divider lines) were invisible to non-visual verification. All were caught only when the Orchestrator headless-rendered the running dashboard (`google-chrome --headless=new --screenshot`, then Read and cropped the PNG) during verify-against-disk (Dispatched-worker flow step 6). The COR-T-041 reshape reinforced the pattern: the Orchestrator headless-rendered each pass before the user gate, catching the E2.1 rollup color and confirming the dept badges.
- pattern: A visual deliverable's correctness lives in the rendered DOM, which the executor's data-layer + build verification structurally cannot reach: render-time crashes (reserved props, undefined access) and layout/styling correctness are invisible to it. The executor's verification was sound for what it covered (data shape, build success); the gap is intrinsic to non-visual checks of a visual surface. The user's visual gate is the backstop, but bouncing to the user for defects a render would catch is expensive and erodes trust. Mitigation established this session: the Orchestrator headless-renders the running deliverable (`google-chrome --headless=new --virtual-time-budget=<ms> --screenshot=<png> <url>`, then Read the PNG, cropping regions with ImageMagick for detail) during step 6, before surfacing to the user. Candidate promotions: (a) a written sub-step in the Dispatched-worker flow step 6 ("for a visual deliverable, headless-render and inspect the running surface before the user gate"); and/or (b) an executor convention that a visual-surface executor attempt a headless render as part of its own verification. Until promoted, the Orchestrator renders visual deliverables before the user gate. Logged after two reinforcing instances (COR-T-040 blank page + styling; COR-T-041 reshape) per the user (2026-06-12).

- context: During COR-T-050 phase-1 verification the running dashboard showed `current_phase: 3` / `next_step: ""`. Phase 2's only filed epic, `DB-E-001` (database), was done, and the Backend API epic existed only in intent (the `backend-api` workspace had no `epics/` tree yet, lazy creation), so Phase 2 rolled up as done and `current_phase` advanced to Phase 3 (mcp-server, which has no epics and so yields an empty `next_step`). - pattern: A derived completeness surface is only as correct as its source files are complete. An epic that exists in intent but not as a file makes its phase read prematurely done. This is the flip side of the ADR-037 / ADR-040 full-derivation push and a continuation of the COR-03 lineage: each derivation removes a hand-maintained surface but introduces a new correctness dependency (here, eager epic filing). Candidate mitigations: (a) discipline - file a department's forming epic when the department is stood up, so no active phase is ever epic-empty while work is anticipated; (b) a dashboard consistency check (the ADR-036 check family, owned-but-advisory per ADR-035/ADR-039) that flags a phase reading done while a rostered member department has a non-empty task tree but no epic in that phase; (c) a derivation-semantics change (a phase is not done unless every rostered member department has an epic in it). ### COR-09: a green test one-shot is not a runtime gate; service deliverables need a boot smoke at close

- date: 2026-06-15
- state: logged
- context: API-T-002 (the FastAPI `api` service) closed green: the `api-test` compose one-shot passed 19/19 and the orchestrator independently re-ran it at close. But the suite injects the admin env via `monkeypatch.setenv` (conftest/test fixtures), so it never exercised real boot; `docker compose up api` then crashed on `RuntimeError: ADMIN_EMAIL is not set` (the app's correct fail-fast, but an uncovered path). Separately, the `gen-admin-hash.sh` dev helper (an orchestrator-direct one-off) was smoke-tested for its `.env`-write logic but not against `up api`: the argon2id hash it wrote to `app/.env` contains `$` (`$argon2id$v=19$...`), which docker compose interpolated as `$variables` and blanked, corrupting the stored hash so login would 401 -- visible only on a real boot. Both were caught when the user ran `up api`, not by the close gate (which re-ran the test one-shot) nor by the one-off's logic smoke. (A third, environmental, instance followed: a compose network desync left the api container unattached to `app_default`, only visible on `up`.)
- pattern: A passing test suite (and unit/logic smoke) is not a runtime gate. Tests and fixtures inject configuration and bypass the deployment substrate -- env-file interpolation, secret/`$` escaping, compose networking, the startup lifespan -- that only the real boot path exercises. This is the runtime cousin of COR-07 (visual deliverables need a render, not just a data/build check): in both, the deliverable's correctness lives in a surface the test/unit layer structurally cannot reach. Candidate promotions: (a) a Dispatched-worker-flow step-6 sub-step, parallel to COR-07's render sub-step -- "for a runnable service deliverable, boot the real service (`compose up`) once and confirm clean startup before the user gate," not just the test one-shot; (b) an executor convention to attempt a real boot as part of its own verification when it builds a runnable service. Until promoted, the orchestrator boots service deliverables at close. Logged after two instances this session (API-T-002 missing-env; `gen-admin-hash.sh` `$`-corruption) per the user (2026-06-15).

### COR-10: tooling shipped against an assumed harness contract that was actually inverted

- date: 2026-06-24
- state: logged
- context: COR-T-057 shipped `bin/seed-worktree` as the `WorktreeCreate` hook for the ADR-046 worktree-per-session workflow. It was written on the assumption that the harness creates and checks out the worktree, then calls the hook to *seed* it (copy `.env`, set `core.hooksPath`, build compose) -- so the script only `mkdir`'d an empty `app/` and seeded into it, never running `git worktree add`. The actual documented contract (code.claude.com/docs/en/worktrees) is the inverse: a `WorktreeCreate` hook "replaces the default `git worktree` logic entirely" -- the hook itself must create AND populate the worktree and print its path to stdout. Result (COR-T-058): the first real worktree creation failed end-to-end (tracked files absent -> `docker compose build` hit "no configuration file provided" -> `set -euo pipefail` non-zero exit aborted creation, leaving an unregistered worktree and a leftover dir that blocked retry). Fixed by making the hook run `git worktree add <dir> -b <name> master` itself, then seed best-effort. The fix was verified by driving the hook via its documented stdin/stdout contract, not by a real harness invocation.
- pattern: Tooling that integrates with a harness/platform seam can be built against an *assumed* contract that is plausible but inverted, and the gap is invisible until the seam first fires for real (here, the first worktree creation). Cousin of the COR-04/05/06 family (unverified claims), but the unverified claim is structural: "the harness owns step X" baked into the tool's control flow, never checked against the platform's own contract doc. The Agent-Discipline rule (verify before asserting) extends to load-bearing assumptions about external contracts a deliverable depends on. Candidate promotions: (a) a kickoff/executor convention that when a deliverable integrates with a named harness/platform seam (a hook, an env var the harness sets, an I/O contract), the kickoff cites the contract doc and the executor's verification includes exercising or at least reading that contract, not just unit logic; (b) treat "first real firing of a new seam integration" as a verification gate distinct from tests (kin to COR-07's render gate and COR-09's boot gate -- the deliverable's correctness lives in a surface tests structurally cannot reach). First logged instance; promote if a second seam-contract mismatch recurs. Until then, the orchestrator/executor verifies a new seam integration against its platform contract doc before close.
